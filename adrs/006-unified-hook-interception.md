# ADR-006: Unified hook interception to replace setActiveTools removal

**Status:** Accepted
**Date:** 2026-06-27
**Deciders:** [@kkkiio](https://github.com/kkkiio), [@windingwind](https://github.com/windingwind)

## Context

The architecture mode extension has two layers of tool restriction:

| Layer | Mechanism | What it does |
|-------|-----------|-------------|
| Active tools | `setActiveTools(ARCH_TOOLS)` | Replaces the agent's tool list with a hardcoded set |
| Hook interception | `tool_call` hook | Blocks unsafe bash, edit/write on non-document files |

Together they create three independent categories of tool behavior:

| Tool | In ARCH_TOOLS? | Hook guard? | Effect |
|------|:---:|:---:|---|
| `read` | ✅ | — | Always available |
| `bash` | ✅ | Safety filter | Available, restricted |
| `edit` | ✅ | Path filter | Available, restricted |
| `write` | ✅ | Path filter | Available, restricted |
| `grep` | ✅ | — | Added by arch-mode |
| `find` | ✅ | — | Added by arch-mode |
| `ls` | ✅ | — | Added by arch-mode |
| `ask_user_question` | ✅ | — | Added by arch-mode |
| Other extensions' tools | ❌ | — | Removed entirely |

This approach has three problems:

### Problem 1: Destroys other extensions' tools

When architecture mode activates, the hardcoded `ARCH_TOOLS` list replaces the
entire active tool set. Any tools registered by other extensions (e.g., LSP
integrations, custom code generators, specialized analyzers) are silently
removed. The user loses functionality that has no relationship to architecture
mode's restrictions.

### Problem 2: Triggers wasteful system prompt rebuild

`setActiveTools()` calls `_rebuildSystemPrompt()` internally, which constructs
the `Available tools:` section and appends tool guidelines. But architecture
mode immediately overrides the entire system prompt via `before_agent_start`.
The intermediate system prompt generated by `_rebuildSystemPrompt` is never
sent to the LLM — it's pure waste.

This waste also represents an unnecessary side effect: it mutates internal
state (`_baseSystemPrompt`) that the extension doesn't own.

### Problem 3: Redundant control mechanisms

The system prompt tells the agent what tools are available, AND `setActiveTools`
removes them from the agent's tool list, AND `tool_call` hook blocks them.
Three mechanisms doing overlapping work:

- If the model follows the system prompt → hook isn't needed
- If the model ignores the system prompt → hook would block, but `setActiveTools`
  already prevented the tool from being called
- The hook's `reason` messages (richer, context-specific feedback) are wasted
  because `setActiveTools` never lets the model reach those tools

`grep`, `find`, `ls` are the most clear example: they are read-only tools that
are also accessible via `bash`. Removing them from the tool list only to have
the model use `bash grep ...` instead adds no real safety, but fragments the
interception logic.

## Decision

**Replace `setActiveTools`-based tool removal with unified `tool_call` hook interception.**

The new approach:

1. **On entering arch mode:** Add only `ask_user_question` to active tools via
   `pi.setActiveTools([...pi.getActiveTools(), "ask_user_question"])`. No other
   tools are added or removed.

2. **On exiting arch mode:** Remove only `ask_user_question` from active tools
   via `pi.setActiveTools(pi.getActiveTools().filter(t => t !== "ask_user_question"))`.
   No tools are restored from a saved snapshot.

3. **All explicit behavioral restrictions** (unsafe bash, non-document file
   edits, and known disallowed tool usage such as `ask_user_question` outside
   arch mode) are handled by the `tool_call` hook, which returns
   `{ block: true, reason: "..." }` with specific, actionable feedback for each
   blocked attempt.

The `tool_result` hook's disabled-tool error rewriting is removed entirely
(entering architecture mode no longer disables tools).

### System prompt and tools

The `ARCH_SYSTEM_PROMPT` is updated to reflect the current tool set. It lists
the tools that are available and their usage constraints. The system prompt
provides soft guidance; the `tool_call` hook provides hard enforcement.

### What changes

| Before | After |
|--------|-------|
| `ARCH_TOOLS = ["read","bash","grep","find","ls","edit","write","ask_user_question"]` | No hardcoded list |
| `NORMAL_TOOLS = ["read","bash","edit","write"]` | Not needed |
| `previousTools` saved on enter, restored on exit | Not needed |
| `tool_result` hook rewrites errors for disabled tools | Dead code, removed |
| Other extensions' tools removed in arch mode | Preserved |
| `grep`/`find`/`ls` as independent tools | Accessed through `bash` |

### What stays the same

- `tool_call` hook blocking unsafe bash commands (ADR-002)
- `tool_call` hook blocking edit/write on non-document files (ADR-001)
- `tool_call` hook blocking `ask_user_question` outside arch mode
- Stand-down mechanism (ADR-004)
- Persistent state across sessions and forks

## Consequences

### Positive

- **Other extensions' tools preserved.** Tools from co-installed extensions
  remain available in architecture mode. The extension plays well with others.

- **Unified interception.** All blocking decisions flow through the `tool_call`
  hook, producing richer, context-specific feedback messages (the `reason`
  field) that guide the model back to compliant behavior.

- **Eliminates wasteful `_rebuildSystemPrompt` calls.** `setActiveTools` no
  longer triggers an intermediate system prompt rebuild that gets immediately
  overridden.

- **Simpler code.** `ARCH_TOOLS`, `NORMAL_TOOLS`, and `previousTools` are
  removed. `exitMode` no longer needs save/restore logic.

- **`ask_user_question` is the only tool added dynamically.** This is the
  minimum viable change to the active tool set, reducing the blast radius of
  any caching or tool-configuration side effects.

### Negative

- **No "safe by omission" for unused tools.** If a newly-installed extension
  registers a tool that would be inappropriate in architecture mode, the
  `tool_call` hook won't know about it by default. Mitigation: the
  `ARCH_SYSTEM_PROMPT` instructs the model to only use tools listed there.
  If a specific tool becomes a recurring problem, it can be added to the
  `tool_call` hook's blocklist.

### Accepted risk rationale

This is an accepted trade-off rather than an accidental gap:

- In practice, agents usually modify code through the native `edit`, `write`,
  and `bash` tools. Those paths remain explicitly guarded by architecture mode.
- Preserving co-installed extensions is a primary goal of this ADR. Blocking all
  unknown tools by default would make unrelated extension functionality
  unavailable, reintroducing the interoperability problem this decision fixes.
- Architecture mode is an interactive discussion mode: the user is normally
  waiting for the agent's response and monitoring the run. If an unexpected
  extension tool starts executing, the user can manually interrupt the agent.
- If a specific extension tool repeatedly violates architecture-mode intent, it
  should be added to the `tool_call` blocklist with a targeted reason instead of
  treating all extension tools as unsafe.
